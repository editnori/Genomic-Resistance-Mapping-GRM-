# Operational reference

This page preserves verbatim the detailed reuse, derived-output, verification, and deployment-test rules moved out of [README.md](../README.md).

## Pipeline reuse and `grm curate`

Before reusing count, structure, and matrix, the pipeline checks the genome selection and order, k = 31, the matrix minimum support of 2, the catalog version behind the gene calls, and each genome's kset digest (a hash of its k-mers). A mismatch, including stages built by hand at another `--k` or `--min-support`, reruns counting, which reuses ksets on disk at k = 31 and recounts the rest from FASTA, then rebuilds the stages that no longer match. Direct `grm learn` refuses the same mismatches and names the command to rerun.

A learned report is reused only when its evaluation revision and input fingerprint match, its evaluation audit is valid, and no feature records a failed BV-BRC annotation download. A report whose audit is invalid is written for review, but `grm learn` stops with an error instead of logging it as done, and the next run recomputes it. Such a feature has no gene or product and records the error in `annotation_error`, so the next run recomputes its report. The fingerprint hashes the matrix digest, the antibiotic and its MIC breakpoint, the dataset's class minimum, the count of excluded MIC-inferred labels, the evaluation settings, the lineage threshold, the catalog version, and each evaluated genome's reported call, MIC, lineage, and gene calls in matrix order. Because it uses the kset digests recorded in the matrix, deleting ksets with `--drop-ksets` keeps results current, and editing a kset outside `grm count` goes unnoticed. Genome metadata, contig counts, and drug class change only descriptive fields and are left out, so run `grm learn --force` after changing only those. A schema change alone recomputes nothing.

Rerunning `grm curate` is a separate choice. Curation counts only reported calls when it admits datasets and ranks genomes, and older curated files also counted MIC-inferred labels, so a new curation can select other genomes for the pipeline to download and count. A `datasets.json` written before `min_class` was recorded reads as a class minimum of 25, the gate revision 6 applied. After raw records or curation rules change, rerun `grm curate` before the pipeline. A dataset that no longer meets its recorded class minimum loses its saved report when learning reaches it.

## Intervals

`grm intervals` writes `report/intervals/<id>.json` for every dataset `report/index.json` lists: for each learner row of each split, a two-sided 95% Clopper-Pearson (exact binomial) interval for VME, over the resistant isolates the row called (`fn` of `tp + fn`), and for ME, over the susceptible ones (`fp` of `tn + fp`). It is arithmetic on the counts the report already holds; it fits nothing and changes no report file, so a report built without it is byte for byte what it was. A zero denominator gives no interval. Each file records its report's SHA-256, evaluation revision and the counts it used, and the dashboard shows an interval under its VME or ME only where those counts equal the report's, so a file left from an earlier build shows nothing. Run it after `grm report` and before the report tree's manifest is written, so the publication ships the files. Without them, the dashboard works as before. The intervals describe sampling of these isolates under internal cross-validation; they are not calibration, clinical bounds or external validation. The method and reference values are those of the revision-7 offline run (`data/research/grm-all23-saved-intervals-20261027-kimi`, SciPy `beta.ppf`), which `src/intervals.rs`'s tests reproduce to 1e-12.

## Baselines

`grm baselines` writes `report/baselines/<id>.json` for every dataset `report/index.json` lists and it does not refuse: what two predictors that read no genome reach on the report's own folds and isolates. For a report with an MIC model, each MIC fold's training isolates give a constant MIC, the lower median of their exact MICs (and their mode), scored on the fold's exact test MICs by the model's rule, within one doubling dilution. For each split with folds, a lineage-identity baseline scores each test genome at the resistant share of its lineage in its fold's training genomes, or the fold's training prevalence when its lineage is not there, and counts the calls as a learner row's are. The MIC folds are not stored, so the command rebuilds them and checks them against the report's held-out predictions, counting the groups of isolates with bit-identical predictions that lie inside one rebuilt fold (I) and that span folds (X). With X = 0 the folds are confirmed; with X ≤ I the file is written and the dashboard marks the constant †; with X > I that dataset alone is refused, gets no file, and the run ends with an error once the others are written. It fits nothing, reads no network and changes no report file, and each file is pinned to its report's SHA-256 and evaluation revision. It also writes `report/baselines.json`, the MIC constants of every file in one summary for the overview, the datasets table and the methods page, pinned to the SHA-256 of `index.json`'s bytes. The dashboard shows a baseline only where a pin holds; without the files it shows none. Run it after `grm report` and before the report tree's manifest is written, as for intervals. The rules, the file and the release's figures are in [baselines.md](baselines.md), with how the files relate to `research.json`. A baseline describes these cross-validated folds of public data; it is not a clinical figure.

## Provenance and companion documents

`grm fetch genome-dates` fetches BV-BRC's `date_inserted` and `completion_date` for every genome in `species/*/genomes.txt` into `bvbrc/genome_dates.jsonl`, with `bvbrc/genome_dates.manifest.json` pinning it (the lists asked for, the genomes BV-BRC returned no record for, and the file's SHA-256). `grm curate` writes `curated/provenance.jsonl`, each genome and drug pair's record details: methods, standards, record count, MIC spread, the earliest and latest record `date_inserted`, and the sets of testing-standard years, PMIDs and sources. `grm provenance` then writes `report/provenance/<id>.json` for every dataset `report/index.json` lists, pinned to its report's SHA-256 and evaluation revision and to both inputs' SHA-256, and `grm provenance --check` fails when any pin no longer holds. None of it changes a report, a curated file `grm curate` wrote before, an input fingerprint or a learner's input; the dates are source proxies and never predictors. [provenance-fields.md](provenance-fields.md) lists what each field reaches. The dashboard doesn't read these files, and they aren't part of a publication yet: build a report tree bound for release without `report/provenance/`.

[research/genotype-to-phenotype.md](research/genotype-to-phenotype.md) covers diagnostic and surveillance uses, the published evidence, and the validation a clinical claim would still need.

[rule-words.md](rule-words.md) says what a set covering machine rule's words claim on the site, which of them the release's index writes and which the app writes, and how the wording is numbered.

[outside-study-results.md](outside-study-results.md) gives the result of a retrospective test on newly deposited studies from the same database: each revision-12 report's final model, applied unchanged to BV-BRC genomes added after the cohort was built. [outside-study-results-by-species.md](outside-study-results-by-species.md) reads it one species at a time. [outside-study-test.md](outside-study-test.md) is the plan, frozen before any of those genomes was fetched. The output files are in `reference/outside-study/`. The result's section Revision 14 reads the same estimates against the figures the site serves now, from `reference/outside-study-figures/`. `reference/outside-study-models/` holds a digest of each final model in both revisions, and the suite fails if one differs.

[lasso-stopping.md](lasso-stopping.md) gives the lasso's stopping rule and the large-species scan it registered. Its section Revision 14 scan reports the scan of 15 November 2026: the release's lasso code fitted again on the list's 18 datasets, each fit compared with the released reports. The released lasso figures of those datasets are reproduced bit for bit and every fit met the solver's convergence test, which says nothing about accuracy or calibration: recall ranges from 0.1710 to 0.9473 on the random split and from 0.0311 to 0.9385 on the lineage split, lowest for `mycobacterium_tuberculosis__clofazimine` in both. The plan, the result files, the scripts and an independent review of the scan are in `reference/lasso-scan/rev14-20261115/`.

[data-collection.md](data-collection.md) shows how to keep one checked copy of the project's files: `scripts/collect/collect.py` lists them with a size, a sha256 and a class, packs one class into archives of at most 1.9 GB, and checks an archive against the list it carries.

## Deployment tests and result checking

`bash -n` parses only its first file, so `xargs -n1` runs it once per script. The deployment tests run in temporary directories; `apply.sh` needs `cc`, starts stub servers on free loopback ports, injects signals at each step of a start and in the forked child before it execs, and takes about 15 to 20 minutes on a loaded host. Both suites count their assertions and fail when the count differs from the expected total. Their only skips depend on the environment, and each prints a `skip` line and lowers the expected total: the root-only cases in both suites, and in `apply.sh` the user and PID namespace cases where `unshare` cannot create those namespaces. A mutation harness, kept outside the repository, checked that the suites catch each reviewed deployment defect ([deployment.md](deployment.md#checks)).

`scripts/check-results.py` and `scripts/metric-audit/` check saved reports apart from the Rust code that wrote them. The checker recomputes each learner's confusion counts and balanced accuracy from the saved scores; the metric audit also rebuilds the folds with the `foldgen` helper, recalculates the metrics, and checks the run against its backup and log.

`python3 -I scripts/check-results.py data` checks the saved dataset reports and writes `data/logs/result-validation-receipt.json`; `--out <file>` writes the receipt elsewhere, such as outside a read-only data root. Run it without `-O`, which would skip its assertions.

`--log <pipeline log>` also requires every report from revision 7 on to have a `done` line in that log naming its headline learner. A run that reuses a report logs no `done` line for it, so use `--log` only with the log of a run that recomputed every report, such as the first revision-7 run, and keep a copy, because the detached run replaces `data/logs/pipeline.log` each time. After a run that reused reports, use `--skip-log <pipeline log>`, which reads only the skip lines.

Both checkers take the current datasets from `data/curated/datasets.json` and list a result for a dataset no longer curated as "not in current curation" without reading it. A species is checked when it has results or both `genomes.txt` and `counted.json`, and the metric audit also checks every curated species matching a species glob other than `*`. Other curated species are listed as "not run" and do not fail. Every curated dataset of a checked species needs a result unless the skip log (`--skip-log`, or else `--log`) has its exact `too few labeled genomes after download, skipped` line with no later `done` or `recomputing report` line, so with neither option a missing result fails. A skip never exempts an existing report, and both receipts list the exclusions and skips.

`python3 -I scripts/metric-audit/audit.py --help` lists the metric audit's inputs: the evaluation revision, the report backup taken before launch, the run's pipeline log, and its UTC launch time.
